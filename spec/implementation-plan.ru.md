# План реализации неизменяемых данных и ADT в Ixion

18 октября 2026 года. Основание — [целевая спецификация](specification.ru.md).
Это план изменений компилятора. Реализация начата; текущее состояние отмечено ниже.
Этапы идут в порядке зависимостей, каждый завершается проверяемым результатом. Оценки сроков без реализации прототипов не фиксируются.

## Текущее состояние реализации

Третий инкремент: новый синтаксис и AST, параметрические/рекурсивные ADT,
произведения, `case` и неизменяемые списки с функциональным API исполняются через
ASM и генерацию Java. Полная целевая редакция языка ещё не реализована. Запуск проверок на JDK 21:

```sh
JAVA_HOME=/Users/artyom/Library/Java/JavaVirtualMachines/ms-21.0.10/Contents/Home ./gradlew clean test
```

Проверка инкремента: 101 тест, без пропусков и ошибок. Дополнительно выполнен
`test --rerun-tasks`, затем `clean test --no-build-cache` на JDK 21: компиляция
и исполнение повторены без кеша задач.

Ключевые решения и проверки:

- ADT используют общий закрытый `AdtValue` с неизменяемыми payload и reified tag,
  а не отдельный JVM-класс на каждый вариант. Это осознанное изменение предлагаемого
  layout: номинальность и различимость generic-аргументов сохраняются без взрыва
  специализаций, включая полиморфную рекурсию. Формат JVM-классов не является
  языковым ABI.
- `CaseExpression` содержит упорядоченный список ветвей. `PatternChecker` создаёт
  общий `PatternPlan`; `PatternCoverage` проверяет матрицу конструкторов для сумм,
  произведений, bool/unit и Empty/Cons. Guards не закрывают покрытие. Анализ ограничен
  по глубине/числу шагов и при исчерпании бюджета требует покрывающую ветвь.
- ASM использует прямые переходы, Java — немедленно вызываемые suppliers; ранний
  `return` переносится внутренним `CaseReturn`, который ловится ближайшей Ixion-
  функцией/лямбдой. Тесты проверяют сохранение эффектов, short circuit и области видимости.
- Generic-функции проверяются универсально и получают скрытые type tags. Расширение
  чисел выполняется до boxing/erasure. Теги unions нормализуются после runtime-подстановки.
- Сопоставление потенциально совпадающих generic-альтернатив (`T | int`, `Option[T] |
  Option[int]`) отвергается с `pattern.overlapping_generic_union`, вместо угадывания по
  erased JVM-классу. Закрытые именованные варианты ADT не имеют этого ограничения.
- Функциональные типы не ограничены арностью 4: для больших сигнатур используется
  erased `IxFunctionN`. Захватываются значения, включая скрытые теги типов.
- Проверяются генерация Java через javac и исполнение обеих целей, оптимизированный
  режим, вложенные patterns, ранний return, независимость источников `with`, reification,
  негативная рекурсия, неизменяемость и точные parser diagnostics.
- Проверены реальные CLI-запуски ASM и `--java`; javac/java берутся из текущего JDK,
  runtime classpath передаётся явно. Проверяются final-классы произведений и private
  final-поля. Полнота сопоставления учитывает незаселённые payload-типы, в том числе
  `Option[never]`: единственный возможный вариант — `None`.
- Fixtures из `src/test/resources/conformance/cases.json` больше не pending: они
  включены в действующие тесты. Проверки старого postfix-expression поведения пока
  помечены `legacy-expression-assignment`. Запись в поля мигрирована на `with`,
  mutating push — на `append`; тесты не отключались.
- Списки больше не раскрывают `ArrayList`: входные данные копируются, iterator
  запрещает удаление, rest сохраняет тот же контракт. Native-сигнатуры заданы явно;
  `map` получает скрытые runtime-теги результата, включая пустые списки. Mutable
  JVM `List` не считается совместимым с языковым `T[]`.
- Проверяются границы get/updated, исходные значения после всех операций, порядок
  и кратность callbacks, остановка при исключении, снимки for/лямбд, вложенные и
  generic-списки, работа с оптимизацией и обе CLI-цели. Старые примеры прямого
  чтения из списка переведены на обработку Option.

Реализованный синтаксис и ограничения описаны в [руководстве по ADT](../docs/adt.ru.md)
и [руководстве по спискам](../docs/lists.ru.md).

## 2. Этап 0 — зафиксировать исходную точку и правила перехода

Изменения: `src/test/kotlin`, `src/test/resources`, документы и CI.

1. Запустить существующие `./gradlew test` на JDK 21 и записать исходные сбои.
2. Выделить legacy-fixtures для изменяемых списков, старых generic-структур,
   старого `case` и индексации. Не считать эти сценарии требованиями новой семантики.
3. Завести набор conformance-примеров по разделам спецификации: positive/negative,
   ожидаемая категория ошибки и исходный диапазон. До появления реализации
   хранить будущие сценарии отдельно от обязательного зелёного набора.
4. Выбрать границу перехода: отдельный несовместимый выпуск. При необходимости
   временного режима legacy выбирать его для всего compilation unit и зависимостей,
   запрещая смешивание контейнеров двух версий. Не менять семантику молча по файлам.

Готовность: воспроизводимый baseline, список ожидаемых несовместимостей,
зелёный обязательный набор для каждого промежуточного PR.

## 3. Этап 1 — семантическая модель типов и деклараций

Изменения: `runtime/IxType.kt`, `StructType.kt`, `UnionType.kt`, `GenericType.kt`,
`typechecker/TypeResolver.kt`, `TypeUtils.kt`, `api/Context.kt`, `SemanticVisitor.kt`.

- Ввести идентификаторы типа `(module, declaration)`, параметров типа и вариантов.
  Представить `TypeParameter`, `AppliedType`, `TupleType`, `FunctionType`,
  `AdtType`, `UnitType`, `NeverType`; сохранить прозрачные aliases отдельно.
- Сделать семантические ключи типов неизменяемыми; одинаковые типы должны иметь
  одинаковый hashCode. Не использовать изменяемые JVM-имена как ключи таблиц.
- Разделить тождество типа, возможность присваивания, числовое расширение,
  подстановку параметров и вычисление общего типа выражений.
- Нормализовать unions с раскрытием aliases и устранением `never`; реализовать
  направленные правила `any`, инвариантность контейнеров и уникальность включения.
- Сначала собирать сигнатуры всех типов и функций модуля/зависимостей, затем поля
  и тела. Обнаруживать циклы aliases, недопустимую рекурсию и утечку приватных типов.
- Отделить сведения JVM-представления в сервис backend type layout; текущую
  специализацию структур адаптировать через этот слой, не удаляя её вслепую.

Проверки: одинаковые имена в разных модулях не совпадают; `Box[int] != Box[string]`;
`any -> int` запрещено; `int[] -> any[]` запрещено; циклы aliases диагностируются;
взаимная рекурсия разрешается независимо от порядка объявления.

Готовность: типовая модель работает без ADT-кодогенерации и не использует
`Any::class.java` как универсальное разрешение несовместимых типов.

## 4. Этап 2 — синтаксис и AST нового ядра

Изменения: `lexer/TokenType.kt`, `LexerImpl.kt`, `parser/ReservedWords.kt`,
`Parser.kt`, prefix/infix parselets, `ast/*`, `ExprVisitor.kt`, `StatementVisitor.kt`,
`optimizer/ConstantFoldingVisitor.kt`.

- Перенести generic-параметры структур после имени; разобрать `Type[T]`,
  `Type[T]::Variant`, tuple/function types, `unit`, `never` и `()`.
- Добавить объявления вариантов с полями, кортежи, functional update `with`,
  `CaseExpression` и `CaseBranch(pattern, guard, body)` со списком ветвей.
- Ввести отдельную иерархию `Pattern`: wildcard, binding, literal, constructor,
  struct, tuple, list/rest, type. Каждому узлу сохранять исходный диапазон.
- Развести присваивания-операторы и выражения, `block` функции и `block_expr`
  результата ветви. Удалить синтаксическую проверку обязательного return из парсера.
- Обновить visitors и optimizer так, чтобы неизвестные новые узлы нельзя было
  случайно пропустить. Ввести явное различение type application и index access.
- Применить единые запятые, `return ()` и квалификацию `module::Type`;
  старые формы отклонять с подсказкой миграции.

Проверки: AST snapshots для вложенных шаблонов, нескольких ветвей `Some`,
guards, `[]`, `[x, ..xs]`, `(x,)`, generic-union типов, `with` и конфликтов имён.
Негативные примеры: повторные поля, ошибочные rest-шаблоны, пустой enum,
неоднозначная специализация и недопустимые запятые.

Готовность: все примеры спецификации разбираются, исходные диапазоны сохранены,
но ещё не реализованные конструкции дают контролируемую диагностику.

## 5. Этап 3 — привязки, неизменяемые произведения и замыкания

Изменения: `SemanticVisitor.kt`, `TypeCheckVisitor.kt`, `api/Context.kt`,
оба codegen visitors, `BytecodeGenerator.kt`, lambda runtime.

- Хранить mutability у символа привязки отдельно от типа значения.
  Разрешить присваивание только локальному `var`; запретить верхнеуровневый `var`.
- Проверять запись в поле/индекс до кодогенерации и не допускать её через `any`.
- Генерировать final-классы структур/кортежей, private final поля и read-only доступ,
  полную инициализацию в конструкторе, отсутствие setter-методов.
- Lower `with` в временную базу, временные новые поля и вызов конструктора:
  порядок вычисления и однократное вычисление важнее оптимизации копирования.
- Реализовать `unit` в JVM `V`-контекстах и boxed-контекстах; `never` как
  незавершающийся поток, а не объект-заглушку.
- Реализовать snapshot-захват локальных `var` и `const` лямбдой; хранить захваченные
  данные в final полях, запретить присваивание capture. Убрать арность 4 как
  ограничение языка через генерируемые интерфейсы либо единый адаптер вызовов.
- Ввести анализ допустимости данных: внешние ресурсы не могут скрываться
  в произведениях, `any` или захватах, помещаемых в контейнеры.

Проверки: aliasing структуры не меняет старое значение; `with` вызывает эффектные
выражения один раз слева направо; замыкание видит старое значение `var`;
попытки записи отклоняются; generic-контейнер с ресурсом запрещён.
Проверить final-поля и корректность bytecode через ASM verifier.

Готовность: неизменяемые структуры/кортежи и локальное переприсваивание исполняются
одинаково через ASM и сгенерированную Java.

## 6. Этап 4 — параметрические и рекурсивные ADT

Изменения: разрешение типов, `EnumStatement`, новый ADT runtime/layout,
`TypeCheckVisitor.visitCall`, оба бэкенда, загрузка/экспорт классов в `IxApi.kt`.

- Ввести сигнатуры конструкторов: параметры варианта и результат `Adt[T, ...]`.
  Решать ограничения generic-параметров по аргументам и ожидаемому типу.
- Проверять тела generic-функций универсально; специализация не должна разрешать
  недопустимую операцию только потому, что первый вызов использует `int`.
- Выбрать базовое JVM-представление: закрытый базовый ADT и final-классы вариантов,
  final payload, singleton для варианта без данных. Generic-поля можно boxing/erasure,
  но семантическое тождество параметров сохраняется отдельно.
- Для recursive ADT использовать ссылочные поля; генератор должен регистрировать
  классы заранее и не порождать бесконечные специализации. Для полиморфной рекурсии
  использовать стирание вместо бесконечной мономорфизации.
- Реализовать runtime type descriptors для generic-типов и тегов union. Одна только
  `instanceof` не различает `Box[int] | Box[string]`.
- Проверить экспорт полного набора вариантов, стабильные module-qualified имена
  и отсутствие коллизий генерируемых классов.
- Ввести предопределённые `Option`, `Result` через тот же механизм деклараций,
  а не отдельные исключения в checker/codegen.

Проверки: `Option[int]`, `Result[string, Error]`, дерево и взаимно рекурсивные типы,
явный/контекстный вывод `None`, ошибочная арность и payload, разные generic-альтернативы
union, boxing примитивов, импорт ADT из другого модуля.

Готовность: ADT создаются и передаются между функциями/модулями; параметры
не теряются в runtime-проверках. Деструктуризация завершается на следующем этапе.

## 7. Этап 5 — полноценный `case` и анализ потоков

Изменения: Pattern checker, новый coverage/usefulness analyzer, typed match IR,
`TypeCheckVisitor.kt`, codegen, `MatchCoverageException.kt` и новые diagnostics.

1. Типизировать каждый шаблон относительно scrutinee, ввести локальные immutable
   привязки и проверить guard как `bool`. Сохранить порядок ветвей.
2. Реализовать матричный алгоритм полезности/покрытия по конструкторам. Представить
   структуры и tuple как произведения, enum/bool/unit как конечные наборы,
   списки как Empty/Cons. Числа/строки/`any` требуют покрывающей ветви.
3. Исключать guards из покрытия, но проверять guarded-ветви на перекрытие
   предыдущими безусловными. Генерировать witness неполноты и диапазон недостижимой
   ветви. Ограничить ресурсы анализа без молчаливого принятия неполных матчей.
4. Создать общее typed decision IR: тест тега/литерала/длины, извлечение данных,
   guard, переход к ветви. Сначала использовать корректную последовательную
   стратегию; объединение тестов — последующая оптимизация.
5. Lower IR в ASM и Java: scrutinee во временной переменной, guard ровно один раз,
   единая результирующая переменная/метки для `case`, без извлечения payload
   до проверки конструктора.
6. Перенести проверку возвратов в анализ потоков после типизации `case`.
   Учитывать `never`, полный `case`, обе ветви `if` и ранние `return`.

Проверки: `Some(true)`/`None` неполон для `Option[bool]`; `Some(x) if ...` не закрывает
вариант; `[x, ..xs]` плюс `[]` полны; повторная ветвь после `_` отклоняется;
проверить cross-product вложенных bool/enum, глубоко рекурсивные формы,
эффектные scrutinee/guards, ранний возврат и объединение результатов ветвей.

Готовность: пример рекурсивного вычислителя ADT и обработка `Result` проходят
обоими бэкендами; неполнота выявляется до генерации кода.

## 8. Этап 6 — неизменяемые списки и стандартная библиотека

Зависит от Option/generics и `case`. Изменения: `CollectionUtil.kt`, `ListType.kt`,
`Prelude.kt`, `Modules.kt`, обработка списков/индексации/for в обоих бэкендах.

- Заменить `IxListWrapper` контейнером со скрытым хранилищем: defensive copy входа,
  отсутствие mutable getter и удаляющего iterator. Первая версия может копировать
  массив при обновлении; persistent tree/vector — отдельная оптимизация.
- Реализовать `append`, `concat`, `get`, `updated`, `map`, `filter`, `fold` по
  типизированным Ixion-сигнатурам. `get`/индексация и `updated` возвращают Option.
- Удалить mutating `push`/`pop`; добавить диагностику с заменой на новый API.
- Унифицировать вывод элементов литерала с ожидаемым `T[]`; запретить вывод
  пустого списка без контекста и неявное превращение в `any[]`.
- Реализовать списковые patterns/rest без выдачи изменяемого view. Хвост может
  разделять только неизменяемое хранилище. Проверить snapshot-семантику `for`.

Проверки: сохранение старого списка после всех операций, отрицательные и граничные
индексы, пустые и вложенные списки, порядок callback в map/fold/filter,
внешняя попытка изменить входной массив/iterator, отсутствие aliasing утечек.

Готовность: ни один путь создания/передачи списка не позволяет менять данные;
полный функциональный API работает с primitive и generic элементами.

## 9. Этап 7 — равенство, внешние адаптеры и завершение перехода

- Реализовать структурное равенство/хеширование через общий runtime-контракт.
  Согласовать ASM и Java для float: стандартный record equals нельзя принимать
  автоматически из-за выбранных правил NaN и знакового нуля.
- Проверять возможность равенства по компонентам типа; функции, ресурсы, `any`
  и неограниченные generic-параметры должны диагностироваться статически.
- Описать явные Ixion-сигнатуры std/http/strings/async вместо небезопасного
  вывода mutability/nullability по отражению JVM-метода. Nullable преобразовывать
  в Option, mutable collections копировать, ресурсы маркировать транзитивно.
- Обновить README, `docs/ru.md`, `docs/en.md`, examples, тестовые fixtures и
  подсветку `editors/`. Все позитивные примеры новой спецификации включить в suite.
- Свести дублирующийся frontend compile/compileToJava к общим проходам, чтобы
  правила экспорта, типов и диагностики не расходились.
- Прогнать CI на JDK 21; проверить ASM verifier, сборку сгенерированной Java через
  javac с реальным runtime classpath, запуск, результат и категории ошибок.
  Сравнивать значения/эффекты, а не внутренние имена классов или оформление toString.

Готовность: целевая семантика доступна целиком, документация согласована,
legacy-сценарии либо мигрированы, либо явно отклоняются с полезной подсказкой.

## 10. Порядок поставки и критерий завершения

```text
0 baseline -> 1 типы -> 2 AST -> 3 произведения/привязки
                                   -> 4 ADT -> 5 case -> 6 списки -> 7 интеграция
```

Каждый этап может состоять из нескольких PR: сначала модель/проверки, затем
lowering и оба бэкенда. Нельзя объявлять поддержку конструкции завершённой
только по успешному разбору или только по работе одного backend.

Первый полезный промежуточный результат после этапа 5: `const`/локальный `var`,
immutable struct/tuple, generic recursive enum, `Option`/`Result`, вложенные
шаблоны и полный `case` с одинаковым JVM/Java поведением. Выпуск новой редакции
требует также этапов 6–7: иначе заявленная глубокая иммутабельность нарушается
старым списковым runtime или внешним API.

Главные технические риски: смешение типа с JVM-представлением; существующая
мономорфизация рекурсивных generic-типов; теги erased unions; сложность вложенного
coverage; утечки mutable Java-объектов и расхождение двух бэкендов. План устраняет
их отдельными проверяемыми этапами до оптимизации производительности.
